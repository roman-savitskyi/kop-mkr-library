# МКР: «Бібліотека» — знайди, виправ, поясни

Модульна контрольна робота з курсу «Компонентне програмування». Теми: Л1–Л8 (JSX, компоненти, props, state, події, життєвий цикл, хуки, форми, власні хуки, React Router).

**Час:** 80 хвилин. **Максимум:** 20 балів.

## Завдання

У застосунку «Бібліотека» є баги — місця, де поведінка не відповідає [специфікації](SPEC.md) або React видає помилки/попередження в консолі.

1. **Знайдіть** баг: запустіть застосунок, перевірте його поведінку за специфікацією, читайте код.
2. **Виправте** його мінімальною зміною коду.
3. **Опишіть** його у `REPORT.md` за шаблоном.

Багів більше, ніж потрібно для максимальної оцінки — знайти всі не обов'язково.

## Як працювати (покроково)

1. **Отримайте проєкт:** `git clone https://github.com/roman-savitskyi/kop-mkr-library.git` або на GitHub **Code → Download ZIP** і розпакуйте.
2. **Запустіть** застосунок (див. «Запуск» нижче) і відкрийте DevTools.
3. **Прочитайте [SPEC.md](SPEC.md)** і пройдіть застосунок як користувач: кожну сторінку, кожну кнопку, кожне поле, перезавантаження (F5), кнопки «Назад»/«Вперед». Стежте за консоллю і вкладкою Network.
4. **Помітили розбіжність** зі специфікацією або помилку в консолі — знайдіть місце в коді, яке за це відповідає.
5. **Виправте** мінімальною зміною і перевірте, що тепер усе працює за специфікацією.
6. **Одразу опишіть** баг у `REPORT.md` — не залишайте на кінець пари.
7. Повторюйте кроки 3–6. За 10 хвилин до кінця — переходьте до здачі.

> **Порада.** Деякі баги «ховають» інші: поки не виправлено одне, інше просто неможливо побачити. Почніть з того, що ламає найбільше.

## Звіт (`REPORT.md`)

Звіт пишеться у форматі **Markdown** у файлі `REPORT.md` (шаблон уже є в проєкті). Кожен баг — окремий розділ `## Баг N`. Приклад заповненого опису (баг вигаданий, у цьому проєкті його немає):

```markdown
## Баг 1

- **Де:** `src/components/Counter.jsx`, рядок 12
- **Симптом:** натискаю «+1» → число на екрані не змінюється, хоча в консолі видно, що значення збільшується. За SPEC число має збільшуватися одразу.
- **Причина:** значення лічильника зберігається у звичайній змінній `let count`, а не в стані. Зміна звичайної змінної не викликає повторного рендеру, а при кожному рендері вона знову стає 0.
- **Виправлення:** замінив `let count = 0` на `const [count, setCount] = useState(0)`, а в обробнику — `setCount(count + 1)`.
- **Матеріал курсу:** Лекція 3, слайд «Внутрішній стан» — «зміна state через сеттер спричиняє ре-рендер компонента»; звичайна змінна такого не робить.
- **Тема:** state
```

Пишіть **своїми словами**: потрібно показати, що ви розумієте причину, а не лише знайшли рядок.

**Аргументуйте на основі матеріалів нашого курсу.** Для кожного бага вкажіть лекцію і слайд з [порталу курсу](https://roman-savitskyi.github.io/KOP/), де описано правило, яке порушено. Загальні пояснення «як у React» чи посилання на сторонні статті й документацію без посилання на матеріал курсу оцінюються лише частково. Для багів, що порушують лише бізнес-правила, достатньо послатися на відповідний пункт [SPEC.md](SPEC.md).

## Запуск

```bash
npm install
npm run dev
```

Відкрийте адресу з терміналу (зазвичай http://localhost:5173). Корисно тримати відкритими DevTools: **Console**, **Network**, **Application → Local Storage**.

## Правила

- Єдине джерело правди — [SPEC.md](SPEC.md). Код, що не порушує специфікацію і не спричиняє помилок/попереджень у консолі, **не є багом**.
- **Коментарі в коді можуть бути хибними** — як і в реальних проєктах. Довіряйте лише SPEC і реальній поведінці застосунку.
- Виправляйте **мінімально**. Не переписуйте файли, не рефакторте, не міняйте стилі чи структуру проєкту. Кожна зміна коду, не пов'язана з описаним у звіті багом, **знижує оцінку**.
- Не змінюйте `public/books.json`, `package.json`, `SPEC.md`.
- **Використання ШІ-асистентів (ChatGPT, Claude, Copilot, Cursor, Gemini тощо) для пошуку чи виправлення багів і написання звіту заборонене.** Роботи з однаковими виправленнями або формулюваннями, а також з ознаками згенерованого тексту, оцінюються в 0 балів або вибірково перевіряються.
- Не видаляйте й не змінюйте `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules`, `.windsurfrules`, `.github/` — це вважається порушенням правил МКР.

## Оцінювання

За кожен баг — від 1 до 2 балів залежно від складності:

- **повний бал** — баг виправлено коректно **і** в звіті є симптом, причина, виправлення та **коректне посилання на матеріал курсу** (лекція + слайд);
- **половина** — виправлено, але пояснення відсутнє, неправильне або без посилання на матеріал курсу; або правильно описано без виправлення;
- **0** — якщо після «виправлення» поведінка досі не відповідає специфікації.

Зайві зміни коду (див. «Правила») — штраф.
